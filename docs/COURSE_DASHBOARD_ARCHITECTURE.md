# Course Dashboard Architecture

This document defines the technical/content scaffolding for the AI for Managers course dashboard. It is intentionally content-neutral: builders own lessons, examples, rubrics, assessments, and weekly student-build content. Anthony implements approved material after review.

## Course shell

The dashboard should provide stable destinations for:

- Course Home
- Course Overview
- Weeks 1–15
- Assignments
- Quizzes & Tests
- Discussions
- My Progress
- Resources / Key Terms
- GitHub Help
- Final Dashboard / Project

## Standard weekly page

Every week should use the same content order so builders can hand off material consistently:

1. Week Overview
2. Learning Objectives
3. Required Learning Materials / Lesson
4. Key Terms
5. AI Activity
6. Your Dashboard Build
7. Step-by-Step Student Directions
8. Example / Model
9. Submission Requirements
10. Rubric / Grading
11. Quiz / Test / Discussion when applicable
12. Resources
13. Week Progress

## Student project progression

The student's AI Management Dashboard is a progressive semester project. The technical shell should allow each week to add or revise a component without forcing students to restart the project.

Planned component checkpoints:

| Week | Dashboard component / milestone |
|---|---|
| 1 | Home, purpose, target user, management problem, navigation, future placeholders |
| 2 | AI Tools comparison |
| 3 | Prompt Library |
| 4 | AI Productivity |
| 5 | Manager Decision Assistant |
| 6 | AI Ethics Checker / Risk Assessment |
| 7 | Responsible AI Policy |
| 8 | Manager AI Assistant |
| 9 | AI Verification |
| 10 | AI Use / Disclosure Log |
| 11 | Values-Based AI Decision Framework |
| 12 | Workforce Impact |
| 13 | AI Implementation Plan |
| 14 | Testing, peer feedback, and revision |
| 15 | Final integrated dashboard and reflection |

These are architecture placeholders, not replacement lesson plans. Builders may improve the sequence when the team agrees and should coordinate changes with adjacent weeks.

## Progress architecture

Track two kinds of progress:

### Course progress

- Current week out of 15
- Weekly lesson/activity completion
- Assignment status
- Quiz/test status
- Discussion status
- Overall course completion

### Dashboard-build progress

Track completion of each major dashboard component above. A component should support at least: planned, in progress, submitted, tested, and complete where the UI supports those states.

## Submission architecture

Each weekly assignment area should support:

- Assignment description
- What to submit
- Dashboard build requirement
- Supporting files/link(s), if required
- Student confirmation/checklist
- Rubric or grading criteria
- Submission status

Assessments should have separate containers for quizzes/tests and discussions so the course navigation remains predictable.

## Resources architecture

Maintain a central Resources / Key Terms area. Weekly builders can add approved terms and resources without changing the overall navigation.

## Student testing

Before a weekly page is considered ready, test it as an undergraduate student:

- Can the student find the week's work?
- Are directions understandable without developer knowledge?
- Is the expected deliverable obvious?
- Does the submission area match the assignment?
- Do links work?
- Does the page work on desktop and mobile widths?
- Does the new build connect to prior dashboard work?
- Does previously built functionality still work?

## Scope rule

This architecture is preparation work. Do not pre-write another builder's lesson or assessment just to populate a page. Use placeholders until the builder package is approved.
