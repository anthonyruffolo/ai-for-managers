## Component states

Use these states instead of a single checkbox:

- **Planned** — approved requirement exists but is not represented in the dashboard.
- **Module defined** — the week, instructions, and named artifact exist, but the artifact is not yet a complete interactive student build.
- **Implemented** — the student can perform the intended build/workflow in the dashboard.
- **QA pending** — implementation exists but still requires the documented student-view/regression test.
- **Tested** — the student flow, links/instructions, persistence where applicable, and earlier functionality have been checked.
- **Complete** — approved, implemented, tested, and ready to remain on `main`.

## Course progress

The class dashboard should separately track:

- Current week / 15
- Weekly learning completion
- Assignment completion
- Quiz/test completion
- Discussion completion
- Dashboard-build completion

## Quality gate

A dashboard component should not be considered complete merely because content was added. Students should be able to use it, explain it, test it, recognize limitations/risks, and show how it connects to the larger management product.

Before moving an item to **Complete**:

1. Confirm the builder content is approved.
2. Confirm the page matches the weekly template.
3. Test the page from a student perspective.
4. Verify links and submission instructions.
5. Confirm earlier dashboard functionality still works.
6. Review the changed files and commit message.

## Week 14 testing reminder

By Week 14, students should stop adding major features and test the full dashboard, including navigation, links, instructions, spelling, layout, ethics safeguards, verification, disclosures, and usability. They should test another student's dashboard, give feedback, and revise their own system.

## Week 15 completion

The final dashboard should include the required major components, resources/key terms, and final reflection, and should be ready for presentation/defense.
